Este apéndice no es un curso de k6. Es lo mínimo para **correr y leer** el arnés de `be05` sin engañarte, y una lista corta de las formas en que una herramienta de carga te da un número falso con total aplomo. Las tres primeras son las de siempre; la cuarta la cometió el autor de este curso mientras medía `be05`, y se queda acá porque es la más barata de cometer.

Damos por sabido qué es una prueba de carga y qué es un percentil. Lo que probablemente no hayas tenido que hacer es **decidir la forma de la carga**, y en este curso esa decisión es la diferencia entre ver la noche de la Esclusa de Oro y no verla.

> 🧭 **Por qué k6.** Corre en un contenedor, sin instalar nada, con la versión fijada (`D30`: `grafana/k6:1.5.0`); sus scripts son JavaScript, que ya escribes desde la Fase 1; y separa con claridad el modelo de carga del script. Las cifras de este apéndice son de corridas del 19/10/2026 en la máquina del autor, contra el binario de `be05`: las tuyas van a ser otras.

## 1. Instalar nada: k6 en un contenedor

```bash
docker run --rm -i --network <red-del-backend> -e BASE_URL=http://api:3001 \
  grafana/k6:1.5.0 run - < script.js
```

Tres detalles, los tres importan:

- **`run -` y el `<`.** El script entra por la entrada estándar: no hace falta montar un volumen para un archivo.
- **`--network`.** k6 corre en su propio contenedor, y para él `localhost` es **su** contenedor, no tu máquina ni el del backend (§6.3). Ponlo en la misma red de Docker que el binario y háblale por su nombre.
- **La versión exacta.** `latest` cambia sin avisarte, y una cifra que no dice con qué versión se midió no se puede repetir.

Las variables de entorno llegan al script como `__ENV.NOMBRE`.

## 2. El script mínimo

```javascript
// El script mínimo: diez usuarios virtuales pidiendo /health durante diez segundos.
import http from "k6/http";
import { check } from "k6";

export const options = { vus: 10, duration: "10s" };

export default function () {
  const res = http.get(`${__ENV.BASE_URL}/health`);
  check(res, { "status 200": (r) => r.status === 200 });
}
```

La función por defecto es **una iteración**. Cada usuario virtual (VU) la repite en bucle: pide, espera la respuesta, vuelve a pedir. Contra el `/health` de `be05`, en la red de Docker, esos diez VUs hicieron **251.205 iteraciones en diez segundos** (25.120 por segundo), con una mediana de 313 µs y un p95 de 697 µs. Es un número que no significa nada para el giro —`/health` no toca más que un `Ping`—, y por eso sirve de ejemplo: lo primero que hay que preguntarle a un número de carga es **contra qué** se midió.

## 3. Escenarios: quién decide cuándo llega la próxima petición

Esta es la decisión que más pesa, y la que casi nadie toma conscientemente. Hay dos familias:

- **Modelo cerrado** (`constant-vus`, `shared-iterations`, `per-vu-iterations`): hay N usuarios, y cada uno manda la próxima petición **cuando recibe la respuesta** de la anterior. Si el servidor se pone lento, la carga baja sola. Es un grupo de jugadores tocando *girar* apenas ven el resultado.
- **Modelo abierto** (`constant-arrival-rate`, `ramping-arrival-rate`): las peticiones **llegan a una tasa fija**, pase lo que pase con las anteriores. Si el servidor se pone lento, se acumulan. Es tráfico que llega de muchos lados que no se coordinan.

El arnés de `be05` (`server/load/giro.js`) trae uno de cada:

```javascript
const scenarios = {
  pico: {
    executor: "constant-arrival-rate",
    rate: RATE,
    timeUnit: "1s",
    duration: `${Math.ceil((KEYS * 2) / RATE)}s`,
    preAllocatedVUs: 50,
    maxVUs: 500,
  },
  notificacion: {
    executor: "shared-iterations",
    vus: VUS,
    iterations: KEYS * 2,
    maxDuration: "5m",
  },
};
```

Y la medición que justifica tener los dos. Las mismas 3.000 peticiones contra el giro de 2019, con un stock de 1.000:

| Escenario | Forma | Esclusas entregadas |
|---|---|---|
| `pico` a 50, 500 y 1.000 por segundo | abierto, llegadas parejas | **1.000** en las tres |
| `notificacion` con 50 VUs | cerrado, todos a la vez | **1.030 a 1.032** (tres corridas) |
| `notificacion` con 200 VUs | cerrado, todos a la vez | **1.077 a 1.088** (tres corridas) |

Con llegadas parejas, incluso a mil por segundo, cada petición de medio milisegundo casi nunca se solapa con otra, y la carrera del stock **no aparece**. Con cincuenta jugadores girando apenas reciben respuesta, aparece en todas las corridas. La noche de 2025 fue la segunda forma: una notificación a todos a la vez.

> 🧭 **La forma de la carga importa más que su tamaño.** Antes de elegir el ejecutor, pregúntate qué tráfico real quieres reproducir: ¿llega solo, a una tasa, o lo dispara un evento que mueve a todos juntos? La tasa que elegiste no dice nada si la forma es la equivocada.

## 4. `checks`, `thresholds` y lo que cuenta como fallo

Un **`check`** es una aserción que se cuenta, no que detiene: el resumen dice cuántas pasaron. Un **`threshold`** es un criterio de aprobación: si se cruza, k6 lo dice al final y termina con código de salida distinto de cero, que es lo que hace que un pipeline falle (`be08`).

```javascript
thresholds: {
  http_req_failed: ["rate<0.01"],
  "http_req_duration{name:giro}": ["p(95)<500"],
},
```

**Qué cuenta como fallo, por defecto:** cualquier respuesta que no sea `2xx` o `3xx`. Para el giro, un `409 sin giros` es una respuesta de negocio correcta, no un error del servidor. Medido con 150 claves contra diez jugadores de cinco giros —100 giros posibles y 200 `409`—:

| | `http_req_failed` | Umbral `rate<0.01` |
|---|---|---|
| Con `http.setResponseCallback(http.expectedStatuses(200, 409))` | 0,00 % | pasa |
| Sin esa línea | **66,66 %** (200 de 300) | *"thresholds on metrics 'http_req_failed' have been crossed"* |

El servidor hizo exactamente lo mismo en las dos corridas. Lo único que cambió es qué le dijiste a k6 que esperara.

**El desglose que el resumen no muestra.** Un contador con una etiqueta suma todo junto en el resumen; las submétricas —una por valor de la etiqueta— solo aparecen si las nombra un `threshold`. El truco del arnés de `be05` es un umbral que siempre pasa:

```javascript
const responses = new Counter("respuestas");
// …
thresholds: {
  "respuestas{status:200}": ["count>=0"],
  "respuestas{status:409}": ["count>=0"],
  "respuestas{status:500}": ["count>=0"],
},
// …
responses.add(1, { status: String(res.status) });
```

## 5. Leer el resumen

Este es el resumen de una corrida real de `be05`: el giro pesimista, escenario `notificacion` con 200 VUs, con `--summary-trend-stats "med,p(95),p(99),max"`:

```
    CUSTOM
    respuestas.....................: 3000   1777.851217/s
      { status:200 }...............: 2104   1246.86632/s
      { status:409 }...............: 896    530.984897/s
      { status:500 }...............: 0      0/s

    HTTP
    http_req_duration..............: med=64.92ms p(95)=332.6ms  p(99)=834.21ms max=1.21s
      { expected_response:true }...: med=64.92ms p(95)=332.6ms  p(99)=834.21ms max=1.21s
      { name:giro }................: med=64.92ms p(95)=332.6ms  p(99)=834.21ms max=1.21s
    http_req_failed................: 0.00%  0 out of 3000
    http_reqs......................: 3000   1777.851217/s

    EXECUTION
    iteration_duration.............: med=65.74ms p(95)=339.19ms p(99)=834.33ms max=1.22s
    iterations.....................: 3000   1777.851217/s
    vus............................: 200    min=200       max=200
    vus_max........................: 200    min=200       max=200
```

Lo que se lee, en orden:

1. **`http_reqs` y su tasa.** Cuánta carga hubo de verdad. Si no es la que pediste, para acá: el resto mide otra cosa (§6.1).
2. **`http_req_failed`.** Con los estados esperados bien declarados (§4), cualquier cosa distinta de cero es un problema del servidor.
3. **El desglose por estado.** 896 `409` en una carga donde a nadie le falta saldo: en `be05` son reintentos que llegaron con su giro en proceso, y eso solo se sabe cruzando con la base.
4. **`http_req_duration`: la mediana, el p95 y el p99, nunca el promedio.** El promedio de esta corrida no dice nada que la mediana y la cola no digan mejor, y esconde la cola. Por eso el arnés pide `med,p(95),p(99),max`.
5. **`max`** como señal, no como cifra: 1,21 s en una corrida donde la mediana es 65 ms dice que alguien esperó mucho en la fila del bloqueo.

> ⚠️ **Lo que el resumen no puede decirte es si el sistema hizo lo correcto.** Esta corrida tiene `http_req_failed` en cero y un p95 aceptable, y lo mismo tiene el giro de 2019 que entregó 1.078 Esclusas. Las invariantes —cuántas se entregaron, si el saldo quedó negativo— se cuentan en la base, después (`server/load/medicion.sql`). Una prueba de carga mide **cómo** responde; **qué** hizo lo dice otra consulta.

## 6. Los errores que dan números falsos

### 6.1 Medir el generador, no el servidor

Con un ejecutor abierto, k6 necesita VUs libres para lanzar cada iteración a tiempo. Si todos están esperando respuestas, **no lanza la iteración y la descarta**. Medido contra el giro con la entrega en 100 ms, pidiendo 200 por segundo con solo 5 VUs:

```
level=warning msg="Insufficient VUs, reached 5 active VUs and cannot initialize more"
    http_req_duration..............: avg=105.79ms min=102.33ms med=105ms    max=117.4ms p(90)=108.85ms p(95)=110.9ms
    http_reqs......................: 450    44.685644/s
    dropped_iterations.............: 1550   153.917217/s
```

El p95 de 110,9 ms es impecable, y es mentira: se midió a **44,7 por segundo**, no a 200. Cinco VUs con peticiones de 105 ms no pueden hacer más de unas 47 por segundo, y k6 tiró 1.550 iteraciones por el camino. El servidor nunca vio la carga que creías estar probando.

**Cómo se evita:** mira `http_reqs` contra la tasa pedida y `dropped_iterations` contra cero **antes** de mirar cualquier latencia, y dimensiona `maxVUs` con la cuenta: tasa × duración de la petición, con margen. El arnés de `be05` pide 50 por segundo con hasta 500 VUs.

### 6.2 El calentamiento

Los primeros segundos de un binario recién arrancado no son como los siguientes: el pool de conexiones está vacío, las cachés están frías y, en otros lenguajes, el compilador todavía no optimizó. Mezclar ese tramo con el resto sesga la medición, y por eso se mide **aparte**: un escenario para el arranque, otro para el régimen, cada uno con su etiqueta.

```javascript
const shape = { executor: "constant-vus", vus: 100 };
export const options = {
  scenarios: {
    frio: { ...shape, duration: "2s", tags: { fase: "frio" } },
    caliente: { ...shape, duration: "8s", startTime: "2s", tags: { fase: "caliente" } },
  },
  thresholds: {
    "http_req_duration{fase:frio}": ["p(95)>=0"],
    "http_req_duration{fase:caliente}": ["p(95)>=0"],
  },
};
```

Medido contra el binario de `be05` recién arrancado, con 100 VUs pidiendo `/wheels`, en tres corridas: la mediana de los dos primeros segundos fue de **8,6 a 9,7 ms**, y la de los ocho siguientes, de **7,5 a 8,4 ms**. Hay calentamiento, y es chico: un binario de Go abre sus conexiones en milisegundos y no tiene compilador que esperar. Con 100 por segundo parejos, la diferencia ni siquiera apareció. **La lección no es este número**: es que no lo sabías hasta medirlo por separado, y que en otro sistema —una JVM, una caché que se llena con la primera hora de tráfico— puede ser lo que domine la corrida entera.

### 6.3 La red del contenedor

Desde el contenedor de k6, `localhost` es el contenedor de k6:

```
level=warning msg="Request Failed" error="Get \"http://localhost:3001/health\": dial tcp 127.0.0.1:3001: connect: connection refused"
```

Ese es el error fácil, porque falla. El difícil es medir por **otro camino** sin darte cuenta. El mismo binario, la misma carga (200 por segundo contra `/health`), una vez por la red de Docker y otra por un puerto publicado en el host:

| Camino | Mediana | p95 |
|---|---|---|
| Red de Docker (`api11:3001`) | 0,68 ms | 3,39 ms |
| Puerto publicado (`host.docker.internal:<puerto>`) | 1,06 ms | 1,44 ms |

La mediana subió por el puerto publicado y el p95 bajó, en una corrida de cada una. No hay una regla general que sacar de ahí, y ese es el punto: **los dos caminos dan números distintos**. Entre corridas que vas a comparar, el camino es parte de las condiciones de la prueba, y va anotado junto a la versión y la semilla.

### 6.4 Medir la nada

El error que cometió el autor de este curso midiendo `be05`. El binario no llegó a arrancar —un `go build` falló en el contenedor—, el script de la corrida no lo comprobó, y k6 corrió sus sesenta segundos igual:

```
    checks_failed......: 100.00% 3000 out of 3000
    http_req_duration....: med=0s     p(95)=0s     p(99)=0s      max=0s
    http_req_failed......: 100.00% 3000 out of 3000
    http_reqs............: 3000    49.998661/s
level=error msg="thresholds on metrics 'http_req_failed' have been crossed"
```

`http_reqs` dice 50 por segundo, exactamente lo pedido, y el p95 es **cero**. Si solo miras la tasa y la latencia, tienes el servidor más rápido del mundo. Y fíjate en la última línea: k6 **sí** avisó. El umbral de `http_req_failed` que trae el arnés se cruzó, y k6 terminó con código de salida distinto de cero; el que no miró fue el script que lo lanzaba, que siguió adelante y anotó la corrida. **Cómo se evita:** el script verifica `/health` antes de lanzar la carga y aborta si no responde, y **respeta el código de salida de k6**. Un umbral que nadie lee es un comentario.

## 🧩 Cuándo usar qué

| Si quieres reproducir… | Usa | Y no |
|---|---|---|
| Una notificación que mueve a todos juntos | `shared-iterations` o `constant-vus` con muchos VUs | Una tasa pareja |
| Tráfico que llega solo, a un ritmo | `constant-arrival-rate` con `maxVUs` dimensionado | Pocos VUs y una tasa alta (§6.1) |
| Una subida gradual hasta el pico | `ramping-arrival-rate` | Saltar al pico de golpe |
| El arranque de un despliegue | Un escenario `frio` separado del de régimen (§6.2) | Mezclarlos en un solo número |
| Un criterio para el pipeline (`be08`) | `thresholds` sobre `http_req_failed` y el p95 | Leer el resumen a ojo |
| Saber si el sistema hizo lo correcto | Una consulta a la base después de la carga | El resumen de k6 (§5) |
