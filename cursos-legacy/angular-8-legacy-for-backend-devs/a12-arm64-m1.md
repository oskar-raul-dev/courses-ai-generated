# 📎 Apéndice A12 — 🔥 Dependencias problemáticas en arm64 / M1

> Tutorial Angular 8 — Laboratorio clínico · Consulta rápida · **2h**
> Usado por: Fases 0, 14 · Versión cubierta: la cadena nativa del stack — `node-gyp`, `node-sass` **4.14.1** sobre Node **14.21.3**, y el Chromium que abre Karma
> Estado: 🔥 **Opcional por plataforma.** El curso se completa sin abrir este apéndice

**Esto no se lee de corrido.** Es material de consulta: se entra por el índice buscando algo concreto y se sale. Resuelve un solo problema, el del título: **que el Mac del compañero compile** — y, de paso, que el Windows de otro también, porque la mitad de estos errores no son de arquitectura sino de toolchain y aparecen igual en las tres plataformas.

La idea que ordena todo lo demás, y conviene tenerla clara antes de leer una línea: **un `npm install` no solo descarga JavaScript, también compila C++**. Varios paquetes de este stack traen código nativo, y cuando no existe un binario ya compilado para tu combinación exacta de sistema, arquitectura y versión de Node, npm intenta construirlo en tu máquina. Ahí es donde se rompe todo lo de este apéndice, y por eso los mensajes de error hablan de Python, de `make` o de un compilador cuando tú solo querías levantar un frontend.

**Qué queda fuera:** soporte a plataformas fuera del equipo —si alguien llega con FreeBSD o con una distribución exótica, esto no le sirve—; el par `node-sass` ↔ *module version* de Node con su `Unsupported runtime (83)`, que es del **Apéndice A02 §1.1** y está resuelto ahí; por qué en Apple Silicon el número de Node es 14.21.3 y no 12, que es del **Apéndice A03 §1.2**; que un `node_modules` no se comparte entre arquitecturas, que es la advertencia central del **A03 §9**; y **Docker, Colima y los perfiles arm64/amd64**, que son el **Apéndice A13** entero: acá se dice *cuándo* conviene cruzar a un contenedor, no cómo montarlo.

## 1. Dónde estás parado, en treinta segundos

Todo lo demás depende de tres respuestas, y en un Mac con chip M ninguna es evidente: **`node -v` no te dice la arquitectura**, y una máquina arm64 puede estar corriendo un Node x64 sin que nada lo insinúe.

```bash
# 1. La MÁQUINA. arm64 = chip M (M1, M2, M3...). x86_64 = Intel.
uname -m

# 2. El NODE. Y acá esta la sorpresa: en una máquina arm64 esto puede decir
#    'x64' perfectamente. No es un error: significa que tu Node es de Intel y
#    corre traducido por Rosetta. Es, de hecho, lo que el curso recomienda.
node -p process.arch

# 3. Confirmación desde el binario, por si la 2 te dejó dudando.
file $(which node)
# ...Mach-O 64-bit executable x86_64   -> Node de Intel (bajo Rosetta)
# ...Mach-O 64-bit executable arm64    -> Node nativo

# 4. Solo en macOS: ¿este proceso esta siendo traducido AHORA MISMO?
#    Devuelve 1 si si, 0 si no. Sirve para saber si tu terminal entera esta
#    bajo Rosetta, que es una situación que se hereda y no se anuncia.
sysctl -n sysctl.proc_translated
```

**Cómo se leen las combinaciones**, que es lo que de verdad importa:

| `uname -m` | `process.arch` | Dónde estás | Qué esperar |
|---|---|---|---|
| `x86_64` | `x64` | Windows, Linux o Mac Intel | El caso normal del curso; los binarios existen |
| `arm64` | `x64` | Mac con chip M, Node bajo Rosetta | **Lo que recomienda el curso.** Los binarios de Intel existen y funcionan traducidos |
| `arm64` | `arm64` | Mac con chip M, Node nativo | Rápido, y sin binarios precompilados para varias dependencias de 2019 |
| `arm64` | `arm64` en Linux | Contenedor arm64 o servidor ARM | Igual que arriba, con menos suerte todavía |

> 🧠 **La regla que evita la mitad de los diagnósticos torcidos:** **lo que decide si un paquete nativo encuentra su binario no es tu máquina, es tu Node.** Un Node x64 bajo Rosetta pide binarios de Intel, los encuentra, y todo funciona aunque tu procesador sea otro. Por eso "estoy en un M1" no es un diagnóstico completo: la pregunta es *"¿tu Node es x64 o arm64?"*, y hasta que no la respondas no sabes en qué caso estás.

Y de ahí sale la decisión del curso, que ya está tomada y explicada en **A03 §1.2**: en Apple Silicon, Node **14.21.3** —que es x64 y corre bajo Rosetta— es el número, y no hay conversación. Este apéndice explica el mecanismo detrás de esa decisión y qué hacer cuando aun así algo se rompe.

## 2. Por qué un `npm install` compila C++

Un paquete con código nativo se distribuye de dos formas a la vez: el código fuente en C++, y una colección de **binarios ya compilados** para las combinaciones más comunes. La instalación intenta lo fácil primero y cae en lo difícil cuando no lo encuentra:

```
npm install
   │
   ├─ ¿hay un binario precompilado para
   │   <sistema>-<arquitectura>-<module version de Node>?
   │        │
   │        ├─ SI  ──> lo descarga y listo. Segundos.
   │        │
   │        └─ NO  ──> intenta COMPILARLO en tu maquina con node-gyp
   │                        │
   │                        ├─ ¿hay Python?          ─ no ─> falla (§4)
   │                        ├─ ¿hay compilador C++?  ─ no ─> falla (§4)
   │                        └─ si compila: minutos, y funciona
```

**Las tres coordenadas del binario** están literalmente escritas en la ruta donde el paquete lo busca, y esa ruta es el mejor diagnóstico gratuito que existe. Cuando `node-sass` falla, el mensaje nombra una carpeta como `vendor/darwin-x64-83/binding.node`, y ahí está todo:

- `darwin` — el sistema (`darwin` es macOS, `win32` Windows, `linux` Linux).
- `x64` — la arquitectura **de tu Node**, no la de tu máquina (§1).
- `83` — el *module version* de Node, no su número de versión. El 83 corresponde a Node 14, y es el que aparece en el `Unsupported runtime (83)` que **A02 §1.1** documenta con su fix.

> 💡 **Antes de buscar el error en Google, lee la ruta.** Si dice `darwin-arm64-83` y tú creías estar bajo Rosetta, tu Node no es el que pensabas (§1). Si dice `darwin-x64-93`, estás con un Node más nuevo del que el proyecto fija. La carpeta te dice en qué casilla del tablero estás, y eso ya descarta la mitad de las respuestas de internet.

Los paquetes de este stack que pasan por aquí son pocos y conviene tenerlos identificados: **`node-sass`** es el protagonista, y cualquier cosa que instale un navegador o un binario externo (§5) tiene el mismo problema con otra forma. El resto del `package.json` del curso —Angular, NgRx, RxJS, `@ngx-translate`, jsPDF, Bootstrap— es JavaScript puro y no participa de nada de esto.

```bash
# Qué paquetes de tu árbol traen código nativo. Si la lista es corta, tu
# problema también lo es.
npm ls node-sass
find node_modules -name "binding.gyp" -maxdepth 3
```

## 3. `node-sass` en arm64: las tres salidas

El caso central, y el que hace que el Mac del compañero no compile. El diagnóstico previo —el par `node-sass` ↔ *module version* y el `Unsupported runtime`— está resuelto en **A02 §1.1**; acá va lo que A02 declara "la mitad del A12": qué haces cuando además estás en arm64.

**Opción A — Node 14 bajo Rosetta con `node-sass` pinneado**

Qué es: exactamente lo que ya fija el curso. Node **14.21.3** en Apple Silicon (**A03 §1.2**) es un binario x64 traducido por Rosetta, así que `node-sass` **4.14.1** encuentra su binario precompilado de Intel, lo descarga y funciona. No compilas nada.
Cuándo conviene: siempre que se pueda. Es la ruta corta y la que mantiene tu máquina idéntica a la de tus compañeros de Windows y Linux.
El costo: una capa de traducción —perceptible en los builds, no dramática— y tener Rosetta instalado (`softwareupdate --install-rosetta`).
Veredicto: **es la recomendación del curso** y la primera que hay que intentar.

**Opción B — El contenedor**

Qué es: dejar de pelear con tu máquina y montar el ambiente dentro de un contenedor Linux, que es el **Apéndice A13** (su §6 trae el devcontainer ya escrito, y su §5 explica dónde tiene que vivir `node_modules` para que esto no se rompa).
Cuándo conviene: cuando la opción A no basta —porque hay más dependencias nativas que `node-sass`, porque necesitas paridad exacta con lo que corre en producción, o porque llevas media mañana peleando—.
El costo: un runtime de contenedores más en tu máquina, y un ciclo de trabajo distinto (el editor fuera, la compilación dentro). Y un matiz que conviene saber antes de entrar: dentro de un contenedor **arm64** tu Node es arm64 de verdad, no x64 traducido, así que `node-sass` vuelve a no tener binario — el contenedor reubica el problema, no lo borra (**A13 §3**).
Veredicto: es la salida sensata cuando la A se atasca, y la que el 🔥 de la **Fase 0** te invita a explorar.

**Opción C — Cambiar `node-sass` por `sass` (dart-sass)**

Qué es: quitar el compilador nativo y poner el que está escrito en JavaScript, que no compila nada y por lo tanto no tiene arquitectura.
Cuándo conviene: es la dirección a la que fue el mundo —`node-sass` está archivado desde 2020 (**A02 §1.1**, 📝 de época)— y en un proyecto moderno es la respuesta obvia.
El costo, y por qué **no es la receta de este apéndice**: en el CLI **8.3.29** el compilador no lo eliges tú, lo elige el `sass-loader` que el CLI trae por dentro, y `node-sass` viene arrastrado como dependencia del propio `build-angular`. Puede que el loader caiga en dart-sass si no encuentra el otro, y puede que no. Además, dart-sass es más estricto con la sintaxis vieja y tu proyecto está lleno de `@import` sin `@use` (**A02**).
Veredicto: **experimento, no receta.** Si lo intentas, hazlo en una rama desechable y con la suite de estilos delante — y si funciona, escríbelo, porque este apéndice no puede prometértelo.

> ⚠️ **Y el paso que se olvida siempre, sea cual sea la salida: borra `node_modules` antes.** El binario equivocado queda cacheado y sobrevive a un `npm install` normal, así que sigues viendo el mismo error después de haber arreglado la causa, y concluyes que el arreglo no sirvió. Es `rm -rf node_modules` y `npm ci`, no `npm install` a secas (**A03**).

## 4. `node-gyp`, Python y las build tools

Cuando no hay binario, `node-gyp` intenta compilar, y para eso necesita **tres cosas que no vienen con Node**: Python, un compilador de C++ y las herramientas de construcción del sistema. Esto **no es un problema de arm64**: aparece igual en Windows, y es el desarrollo de la ⚠️ de la **Fase 0 §5.1**, que hasta ahora eran dos líneas sin dueño.

**Windows 11** — es donde más falla y donde más fácil se arregla. Hacen falta **Python 3** en el `PATH` y las **Visual Studio Build Tools** con la carga de trabajo *"Desktop development with C++"*. Sin ellas, el primer paquete nativo revienta y el mensaje habla de `gyp ERR!` y de un `MSBuild` que no aparece por ningún lado.

**macOS** — hacen falta las **Command Line Tools de Xcode**, que traen el compilador:

```bash
# Instala compilador y herramientas. Si ya están, avisa y no hace nada.
xcode-select --install

# Comprobar que node-gyp encuentra lo que necesita, sin instalar nada:
node -p process.version
python3 --version
clang --version
```

**Linux** — el paquete de herramientas de construcción de tu distribución (`build-essential` en Debian y derivados) más `python3`.

**Los tres errores que vas a ver, traducidos:**

- **`gyp ERR! find Python`** — no hay Python, o hay uno que `node-gyp` no acepta. Es el más frecuente en Windows.
- **`gyp ERR! stack Error: not found: make`** (o el equivalente con `MSBuild`) — hay Python pero no hay compilador. Faltan las Command Line Tools o las Build Tools.
- **Un muro de errores de C++ con archivos `.cc` y `.h`** — el compilador está y **está compilando**; lo que falla es el código fuente del paquete contra tu versión de Node o de tu compilador. Ese ya no se arregla instalando nada: se arregla cambiando la versión del paquete (§3) o dejando de compilar (opción A o B).

> 🧭 **La distinción que ahorra la tarde:** si el error dice que **falta una herramienta**, instálala y sigue. Si el error es una **catarata de C++**, deja de intentar arreglar el entorno: estás pidiéndole a un paquete de 2019 que compile en un contexto que no conoce, y la salida es el binario precompilado (§3, opción A) o el contenedor (**A13**).

## 5. El Chromium que abre Karma

La **Fase 12** corre la suite con Karma, y Karma **abre un Chrome de verdad** (`browsers: ['Chrome']`, con `karma-chrome-launcher`). Eso no compila nada, así que no es el problema del §2 — pero tiene su propia versión del mismo enredo de arquitecturas.

**El caso simple: Karma no encuentra el navegador.**

```bash
# Karma busca el ejecutable de Chrome donde el sistema lo suele poner, y si no
# lo encuentra falla con "No binary for Chrome browser on your platform".
# La salida es decirselo tu, con una variable de entorno.

# macOS
export CHROME_BIN="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"

# Linux
export CHROME_BIN=$(which google-chrome || which chromium)

# Windows (PowerShell)
$env:CHROME_BIN="C:\Program Files\Google\Chrome\Application\chrome.exe"
```

En un Mac con chip M esto funciona sin drama: Chrome se distribuye con una versión nativa para Apple Silicon, y **el navegador no tiene por qué coincidir en arquitectura con tu Node** — Karma lo lanza como un proceso aparte, no lo carga dentro del suyo. Es la buena noticia de esta sección.

**Dónde sí muerde la arquitectura:** en cualquier herramienta que **se descargue su propio navegador** en vez de usar el que tienes instalado. Ese es el patrón que rompe en arm64, y el síntoma es siempre el mismo — la instalación termina bien y la herramienta falla al arrancar diciendo que no encuentra un ejecutable que sí está en disco, porque el que bajó es de otra arquitectura. Si te pasa, la comprobación es directa:

```bash
# ¿De que arquitectura es el navegador que se descargo esa herramienta?
file <ruta-al-ejecutable-descargado>
```

> ⚠️ El proyecto declara **Playwright** para smoke tests en el alcance del curso, y Playwright es justamente de las que descargan sus propios navegadores (con un comando de instalación propio, aparte del `npm install`). **Ninguna fase lo desarrolla todavía**, así que aquí solo queda el aviso de que pertenece a esta familia de problemas; queda anotado en los pendientes.

> 💡 **En CI, headless y punto.** Un pipeline no tiene pantalla, así que el navegador tiene que arrancar sin interfaz. El `karma.conf.js` de la **Fase 12 §5.1** trae `browsers: ['Chrome']`, que sirve en tu máquina y no en un contenedor: allá se usa la variante headless con los flags de sandbox que el entorno exija. Es configuración de pipeline y no de este apéndice, pero conviene saber de dónde viene el fallo cuando la suite pasa en local y no en CI.

## 7. Higiene de arquitectura

El error más caro de esta familia no aparece al compilar: aparece días después, y casi siempre porque alguien compartió algo que no se comparte.

**Qué NO se comparte entre máquinas.** `node_modules`, jamás — es la advertencia central de **A03 §9** y en arm64 se vuelve todavía más cierta: la carpeta contiene binarios atados a un sistema, una arquitectura y un *module version*. Copiarla desde un Windows a un Mac produce errores que no mencionan ni la copia ni la arquitectura.

**Qué SÍ se comparte.** El `package.json` y el `package-lock.json`, siempre, y son la única forma correcta de reproducir un árbol: `npm ci` los lee, descarga lo que corresponde **a tu plataforma** y recompila lo nativo si hace falta.

**El detalle del lockfile que confunde.** Un `package-lock.json` generado en macOS puede traer dependencias marcadas como opcionales que solo existen en ese sistema —el vigilante de cambios de archivos del sistema de ficheros es el caso clásico—. **Eso es normal y no rompe nada**: npm las salta en las plataformas donde no aplican. No las quites del lockfile "para limpiar", porque le estarás quitando a tus compañeros de Mac algo que sí usan.

**El ritual cuando cambias de versión de Node.** No es opcional y es el que más veces se olvida:

```bash
# 1. Cambiar de versión.
nvm use            # lee el .nvmrc de la Fase 0

# 2. Borrar los binarios de la versión anterior. SIN esto, el paso 3 no sirve.
rm -rf node_modules

# 3. Reinstalar desde el lockfile, no desde el package.json.
npm ci
```

> 💡 **Antes de pedir ayuda, pega esto.** Cuatro líneas que responden casi todo lo que quien te ayude va a preguntar, y que ahorran tres mensajes de ida y vuelta:
>
> ```bash
> uname -m ; node -v ; node -p process.arch ; npm -v
> ```

## 🧭 Cuándo pelear y cuándo meterse en un contenedor

| Situación | Qué haces | Por qué |
|---|---|---|
| Mac con chip M, empezando de cero | Node 14.21.3 bajo Rosetta (§3, opción A) | Es la ruta corta y ya está decidida (**A03 §1.2**) |
| Falla un paquete nativo y el error nombra una herramienta | Instálala (§4) y sigue | Es toolchain, no arquitectura |
| Falla un paquete nativo con errores de C++ | Deja de compilar: binario precompilado o contenedor | Ese muro no se arregla instalando cosas |
| Hay más de una dependencia nativa peleando | Contenedor (**A13**) | Pelear una a una no escala |
| Necesitas paridad exacta con producción | Contenedor amd64 (**A13**) | Tu máquina no es el servidor |
| Llevas más de media mañana peleando | Contenedor (**A13**) | El tiempo es el criterio, y es legítimo |
| El proyecto es tuyo y puedes cambiar el compilador | dart-sass, **en una rama** (§3, opción C) | Con el CLI 8 no está garantizado |
| Karma no encuentra el navegador | `CHROME_BIN` (§5) | No es un problema de arquitectura |
| Un compañero copió `node_modules` | Bórralo y `npm ci` (§7) | La carpeta no es portable, nunca |
| Nada de esto encaja | Las tres preguntas del §6 antes de seguir | Cierran un porcentaje incómodo de casos |

## ⚠️ Advertencias

**El curso se completa sin abrir este apéndice.** Windows 11 es el entorno por defecto y Linux amd64 funciona sin sorpresas. Esto existe para que quien llegue con un Mac de chip M no se quede fuera, y **nada de lo que hay aquí cambia el contenido del curso**: las versiones fijadas siguen siendo las mismas para todos.

**Tu arquitectura no es la de tu Node, y esa es la confusión de origen.** Un Mac arm64 con Node x64 bajo Rosetta se comporta, a efectos de binarios, como una máquina Intel. Hasta que no corras `node -p process.arch` no sabes en qué caso estás, y todo diagnóstico anterior a eso es adivinar (§1).

**Borra `node_modules` antes de reinstalar, siempre.** El binario equivocado sobrevive a un `npm install` y te hace creer que el arreglo no funcionó. Es el error de procedimiento más repetido de todo el apéndice.

**Un `node_modules` no se comparte entre máquinas. Nunca.** Ni por USB, ni por carpeta compartida, ni "es que a mí me funciona y te lo paso". Se comparten `package.json` y `package-lock.json`, y se corre `npm ci` (**A03 §9**).

**Cambiar `node-sass` por dart-sass no está garantizado con el CLI 8.3.29.** El compilador lo elige el loader interno del CLI, no tú, y la sintaxis vieja del proyecto es más frágil de lo que parece. Si lo intentas, que sea en una rama que se pueda tirar (§3).

**Y la que gobierna a todas: pelear con el entorno tiene un límite de tiempo razonable.** Media mañana. Pasado eso, la respuesta correcta no es más constancia, es el contenedor del **Apéndice A13**. Nadie va a evaluar tu capacidad técnica por haber hecho compilar un paquete archivado en 2020 sobre una arquitectura que no existía cuando se escribió.

- https://docs.npmjs.com/cli/v6/commands/npm-ci — `npm ci`, que es el comando del ritual del §7. La versión 6 de la documentación, que es la del stack (**A03**).
- https://developer.apple.com/xcode/resources — las Command Line Tools de Xcode, que traen el compilador que `node-gyp` necesita en macOS (§4).

> ⚠️ Los enlaces pueden haber cambiado o desaparecido; verifícalos. Con este tema hay un riesgo específico: **la mitad de las respuestas que vas a encontrar buscando estos errores son de 2021-2022, cuando el ecosistema todavía se estaba adaptando a Apple Silicon**, y proponen trucos que hoy sobran o que nunca funcionaron. Desconfía de cualquier receta que no diga qué versión de Node asume.

**Orden de lectura sugerido:** si algo acaba de fallar, §1 para saber dónde estás y §6 para identificar el mensaje. Si vas a montar el ambiente en un Mac por primera vez, **A03 §1.2** y después §3 de acá. Si llevas rato peleando, el 🧭 y de ahí al **Apéndice A13**.

## 🧪 Ejercicios (6)

Cortos y de consulta. Los cuatro primeros funcionan en **cualquier plataforma**; los dos últimos necesitan un Mac con chip M.

1. Corre los cuatro comandos del §1 en tu máquina y anota las cuatro respuestas. Ubícate en la tabla de combinaciones y escribe en una línea qué tipo de binarios va a buscar tu `npm install`. Guarda las cuatro líneas: son lo que vas a pegar la próxima vez que pidas ayuda (§7).
2. Corre `npm ls node-sass` y `find node_modules -name "binding.gyp" -maxdepth 3`. Anota cuántos paquetes de tu árbol traen código nativo y cuáles son. Explica en una línea por qué esa lista tan corta significa que tu superficie de riesgo también lo es.
3. Busca en `node_modules/node-sass` la carpeta cuyo nombre tiene la forma `<sistema>-<arquitectura>-<número>`. Descompón las tres partes y verifica el número contra la tabla de *module versions* de las referencias. Confirma que corresponde al Node que declara tu `.nvmrc`.
4. **Rompe a propósito.** Cambia de versión de Node con `nvm use 12` (o la que tengas a mano), corre `npm start` **sin** borrar `node_modules` y anota el error exacto. Después aplica el ritual completo del §7 y confirma que se arregla. Vuelve a la versión del `.nvmrc`.
5. **Requiere Mac con Apple Silicon.** Instala un Node **nativo arm64** (una línea 16 o posterior) en paralelo al del proyecto, cambia a él y corre `npm ci` sobre el proyecto. Anota el error exacto, en qué paquete se produce y si la ruta que menciona dice `arm64`. Después vuelve al 14.21.3 y aplica el ritual del §7. Es el ejercicio que explica de golpe por qué **A03 §1.2** dice lo que dice.
6. **Requiere Mac con Apple Silicon.** Con el proyecto ya funcionando bajo Rosetta, cronometra `npm ci` y `npm run build` y anota los dos tiempos. Después repite las mismas dos medidas dentro del contenedor del **Apéndice A13**. No es un ejercicio de rendimiento: es para que tengas tu propio dato cuando alguien pregunte cuánto cuesta la traducción de Rosetta en este proyecto concreto.
