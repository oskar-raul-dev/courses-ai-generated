## 🟢 Fácil (1–3)

### Ejercicio 1

```text
Did not find any tables named "legacy.Pac*".
```

Es **E-17**. `psql` pasa el patrón a minúsculas y busca `pac…`; en la caja todo empieza con mayúscula. El
patrón que funciona es `\dt legacy."Pac"*`: la parte con mayúsculas entre comillas, el comodín afuera
([`a03`](../a03-clis-de-los-motores.md#-postgresql--psql)). No es un error del servidor: lo escribe el
cliente, y por eso no tiene `ERROR:` adelante.

### Ejercicio 2

```text
ERROR:  invalid input syntax for type numeric: "40.021.044"
```

Es **E-27**, con otro valor: el paciente 2 tiene el DNI escrito con puntos. El mensaje cita el valor
entre comillas, que es lo que hay que buscar en la caja. La conversión que no falla es la de la
[Fase 08](../08-los-dos-extremos-del-mismo-error.md): un `CASE` con una expresión regular, o quitar los
puntos antes (`replace("DNI", '.', '')::numeric`), sabiendo que eso convierte también lo que no era un
DNI.

### Ejercicio 3

```text
ERROR 1305 (42000) at line 2: FUNCTION legacy.similarity does not exist
```

Es **E-22**. MySQL no tiene similitud por trigramas, y una función sin esquema la busca en la base
actual: por eso nombra `legacy.similarity`. Sin `USE`, el error es otro y llega antes:

```text
ERROR 1046 (3D000) at line 1: No database selected
```

MySQL ni siquiera llega a buscar la función, porque no sabe en qué base. La traducción no es otra
función: MySQL no tiene ninguna equivalente (la tabla de traducción de la
[Fase 05](../05-una-persona-no-es-su-documento.md) lo marca con una raya), y la similitud se calcula fuera
del motor.

## 🟡 Intermedio (4–6)

### Ejercicio 4

```text
ERROR:  cannot insert a non-DEFAULT value into column "id"
DETAIL:  Column "id" is an identity column defined as GENERATED ALWAYS.
HINT:  Use OVERRIDING SYSTEM VALUE to override.
```

Es **E-34**. `GENERATED ALWAYS` rechaza un valor que no generó el motor; el `HINT` dice cómo forzarlo.
Es correcto **una vez**: en la carga de una migración, cuando el identificador viene de legacy y hay que
conservarlo, seguida de `setval` al máximo para que la identidad no choque después (E-31). En código de
aplicación, nunca: si la aplicación necesita poner el valor, la columna es `GENERATED BY DEFAULT`
([F10](../10-identificadores.md)).

### Ejercicio 5

```text
ERROR:  could not create unique index "a08_dni_unico"
DETAIL:  Key ("DNI")=(28210797) is duplicated.
CONTEXT:  parallel worker
```

Es **E-21**, sobre la tabla de la caja en lugar del modelo. El DNI que nombra es **el primer duplicado
que encontró**, y no es siempre el mismo: la Fase 05 vio el 9496697 en otra tabla, y aquí, con la
construcción en paralelo, sale el que haya encontrado primero el proceso que lo encontró.
`CONTEXT: parallel worker` dice que lo encontró uno de los procesos que ayudan a construir el índice, no
el principal. Un solo DNI repetido alcanza para que no exista el índice, y la pregunta útil no es cuál,
sino cuántos: `GROUP BY "DNI" HAVING count(*) > 1`.

### Ejercicio 6

```text
ERROR 1170 (42000) at line 2: BLOB/TEXT column 'note' used in key specification without a key length
```

Es **E-37**. MySQL indexa un `TEXT` solo por un prefijo: `CREATE INDEX a08_nota_idx ON lab.a08_nota
(note(100))`. Ese índice sirve para buscar por los primeros 100 caracteres y no puede asegurar unicidad
sobre el texto entero ni ordenar por él. Postgres indexa el `text` entero con un B-tree (hasta el límite
de E-35) y, para buscar adentro, tiene GIN con trigramas, que MySQL no tiene
([F11](../11-indices-y-lo-que-cuestan.md)).

## 🟠 Difícil (7–8)

### Ejercicio 7

```text
-- @engine postgres
-- @setup UPDATE staging.debtor SET balance = 28.00 WHERE debtor_id = 1
-- @check SELECT balance FROM staging.debtor WHERE debtor_id = 1
a1: BEGIN;
a2: SELECT balance FROM staging.debtor WHERE debtor_id = 1 FOR UPDATE;
b1: BEGIN; SET LOCAL lock_timeout = '1s';
b2: UPDATE staging.debtor SET balance = 23.00 WHERE debtor_id = 1;
a3: COMMIT;
b3: ROLLBACK;
-- @permutation a1 a2 b1 b2 b3 a3
```

```text
🏁 lab race · postgres · permutación a1 a2 b1 b2 b3 a3
 a2  1 fila  (28.00)
 b1  BEGIN
 b2  ⏳ espera un bloqueo
   ↳ b2  ✗ 55P03 canceling statement due to lock timeout
 b3  ROLLBACK
 a3  COMMIT
resultado: a sin errores · b con error 55P03 en b2
comprobación: 1 fila  (28.00)
```

Es **E-46**, `55P03`. La permutación que **no** lo provoca es la natural, `a1 a2 b1 b2 a3 b3`: cuando `b2`
queda esperando, el arnés manda enseguida `a3`, el `COMMIT` libera la fila antes del segundo, y `b2`
termina con `UPDATE 1`. Con `b3` antes de `a3`, el arnés espera a `b` (hasta `--patience`), el segundo
vence y el error sale. El mismo escenario es el ejercicio: **el límite de espera solo se ve si la otra
sesión tarda más que él**.

### Ejercicio 8

```text
INSERT INTO a08_presentacion VALUES (11233733, '')
                                               *
ERROR at line 1:
ORA-01400: cannot insert NULL into ("SYSTEM"."A08_PRESENTACION"."OBRA_SOCIAL")

 PROTOCOLO OBRA_SOCIAL
---------- -----------
  11233732 [ ]
```

Es **E-19**. La de `''` no entra, con un mensaje que habla de `NULL` aunque escribiste una cadena: para
Oracle son lo mismo. La de `' '` entra, porque un espacio no es vacío. Postgres aceptaría las dos: `''`
cumple `NOT NULL`. Para que Postgres rechace lo que Oracle rechaza hace falta decirlo,
`CHECK (obra_social <> '')`, y para que ninguno acepte el espacio, `CHECK (trim(obra_social) <> '')` en
Postgres; en Oracle, `trim(' ')` es `NULL`, y un `CHECK (trim(obra_social) IS NOT NULL)`
([F03](../03-lo-que-sql-le-hace-al-modelo.md)).

## 🔴 Muy difícil (9–10)

### Ejercicio 9

```text
-- lost_update.race, REPEATABLE READ
   ↳ b3  ✗ 40001 could not serialize access due to concurrent update
-- write_skew.race, SERIALIZABLE
 b4  ✗ 40001 could not serialize access due to read/write dependencies among transactions
```

Los distingue **el final del mensaje**: `concurrent update` es **E-42**, un conflicto de escritura sobre
la misma fila, y aparece en el `UPDATE` (`b3`), cuando la otra confirma; `read/write dependencies among
transactions` es **E-41**, el SSI que encontró un ciclo entre filas distintas, y aparece en el `COMMIT`
(`b4`). En `psql`, el de E-41 trae además un `DETAIL` con `Reason code`, que `lab race` no muestra. La
aplicación los trata igual porque el remedio es el mismo: **reintentar la transacción entera**, desde el
`BEGIN`, releyendo. El SQLSTATE es el contrato; el texto es para quien diagnostica.

### Ejercicio 10

| Motor | Error | En qué paso | Tomas |
|---|---|---|---|
| Postgres | `40001` (E-41) | el `COMMIT` de `b`; los dos `INSERT` pasaron | 1 |
| MySQL | `1213` (E-43) | el `INSERT` de `b`: los dos tenían el hueco tomado al leer | 1 |
| SQL Server | `1205` (E-79) y después `3902` (E-80) | el `INSERT` de la víctima, que en dos corridas fue una vez `a` y otra `b` | 1 |

**Rúbrica (sobre 4 puntos):**

- **1 punto:** los tres errores con su entrada, y que en los tres queda **una sola toma**: el nivel hizo
  su trabajo, con tres mecanismos (detección de ciclos, bloqueos de rango con *deadlock*, bloqueos con
  *deadlock*).
- **1 punto:** el paso. Postgres deja escribir y frena al confirmar; MySQL y SQL Server frenan al
  escribir, porque bloquean desde la lectura. Una aplicación que solo atrapa errores en el `COMMIT` no
  reintenta en MySQL ni en SQL Server.
- **1 punto:** el 3902 de SQL Server: después del 1205 la transacción ya no existe, y el `COMMIT` que
  sigue falla. La política de reintento no tiene que tratarlo como un error nuevo.
- **1 punto:** una política para los tres: atrapar `40001`/`40P01`, `1213` y `1205` en **cualquier**
  sentencia, deshacer, esperar un tiempo al azar con tope y reintentar desde el principio, un número
  acotado de veces. Y con SQL Server en el laboratorio, `--patience 10`: si no, el arnés puede declarar
  imposible el orden antes de que el motor detecte el *deadlock* (E-102).
