<details>
<summary>✅ <b>Solución de referencia</b> — ábrela después de escribir la tuya</summary>

**Causa raíz**

`src/pages/WheelEditPage.jsx`: el manejador `guardar` no llama a `event.preventDefault()`.
Un `<form>` sin ese paso hace su envío por defecto: el navegador hace una petición `GET`
o `POST` a la URL actual y descarta la página. Todo el estado de React (el borrador de
pesos) se va con ella. La consola guardó lo que pudo, y lo que no llegó a guardarse se
pierde con el parpadeo.

Es el mismo mecanismo de la pista 3, y explica el síntoma completo: la recarga borra el
borrador, y una rueda que sí alcanzó a guardarse aparece con sus pesos nuevos al volver.

**Parche mínimo**

```javascript
async function guardar(event) {
  event.preventDefault(); // el envío lo maneja React, no el navegador
  // …
}
```

**La refactorización correcta**

Un formulario controlado por React siempre tiene su manejador de `submit` con
`preventDefault()` como primera línea. Una regla de lint (`react/...` o una revisión de
formularios) lo previene. La prueba de regresión lo fija para siempre.

**Prueba de regresión**

```javascript
// src/__incidentes__/inc09.test.jsx — la misma prueba que corre en el repo de prueba
test("enviar el formulario de pesos no recarga la página", async () => {
  // …
  const evento = new Event("submit", { bubbles: true, cancelable: true });
  form.dispatchEvent(evento);
  expect(evento.defaultPrevented).toBe(true);
});
```

Con la rama `incidente/09`, la prueba falla (`Expected: true, Received: false`). Con el
`preventDefault()` de vuelta, pasa.

**Prevención**

Un manejador de formulario sin `preventDefault()` es un defecto de revisión: se ve en el
diff. Un test por formulario, como el de arriba, lo caza antes de llegar a UAT.

**Por qué los duplicados**

En la versión vieja de este incidente, la misma recarga creaba la rueda otra vez en cada
intento. En la consola nueva, el equivalente sería reenviar el `PUT` de pesos: como el
`PUT` reemplaza los pesos completos, reenviarlo no duplica segmentos, pero sí pisa un
cambio de otro operador. Es el motivo para tener una sola fuente de verdad: el store.

</details>

**Causa raíz**

`src/features/wheels/wheelSlice.js`: falta el caso `fetchWheels.fulfilled`. El thunk
despacha `pending` (que pone `loading = true`) y, al resolverse, `fulfilled`. Sin el caso
de `fulfilled`, el reducer ignora la acción: `items` no se llena y `loading` no vuelve a
`false`. La pantalla se queda con el cartel para siempre. No hay error porque nada falló:
la promesa se resolvió bien.

En la reproducción con el caos apagado, la respuesta siempre llega, así que el síntoma es
determinista: la pregunta de la primera vuelta no era cuándo pasa, sino por qué en la
máquina de ellos no hay diferencia.

**Parche mínimo**

```javascript
.addCase(fetchWheels.fulfilled, (state, action) => {
  state.loading = false;
  state.items = action.payload;
})
```

**La refactorización correcta**

Un slice con un thunk asíncrono tiene tres casos, siempre los tres. Una revisión que cuente
los casos (`pending`, `fulfilled`, `rejected`) por cada thunk lo caza en el diff.

**Prueba de regresión**

```javascript
// src/__incidentes__/inc10.test.js — la misma prueba que corre en el repo de prueba
test("cuando la lista de ruedas llega, deja de estar cargando", async () => {
  // …
  await store.dispatch(fetchWheels());
  expect(store.getState().wheels.loading).toBe(false);
});
```

Con la rama, la prueba falla (`Expected: 1, Received: 0`, y `loading` queda en `true`).

**Prevención**

Un test por thunk que compruebe el estado final. Es la misma regla que el incidente 06:
el estado que la UI muestra tiene que salir de un caso del reducer, no de la suerte.

**Si tu causa fue distinta a esta**

Si dijiste "la red es lenta", mide: con el caos apagado la respuesta llega en milisegundos,
y el cartel no se quita igual. Si dijiste "es el kiosco", pregunta qué navegador usan: el
slice es el mismo en todas partes.

**Causa raíz**

el servidor las acepta las dos. La prueba lo muestra: el mock queda con dos filas.

**Parche mínimo**

El servidor rechaza un caso ya compensado (409), y el cliente envía el identificador del
caso, no solo el de la petición:

```javascript
// mock/server.js — antes de guardar el envío
if (caseId && db.get("grants").find({ caseId }).value()) {
  return res.status(409).json({ error: "este caso ya fue compensado" });
}
```

```javascript
// src/features/grants/grantSlice.js — el caso es el jugador y el motivo
payload = { ...payload, caseId: payload.caseId || `${payload.playerId}|${payload.reason}` };
```

**La refactorización correcta**

Una compensación necesita una clave de negocio estable (el caso), no un identificador
generado en el cliente. La clave de idempotencia nace del caso, así que dos intentos del
mismo caso dan el mismo resultado sin importar cuántos operadores o pestañas haya. Es la
misma idea que el giro de be05: la clave la pone el cliente, pero la regla de unicidad vive
en el servidor.

```javascript
// src/__incidentes__/inc11.test.js — corre contra el mock real
test("dos operadores no compensan dos veces el mismo caso", async () => {

  const { data } = await axios.get("http://localhost:3001/grants", { params: { playerId: 42 } });

});
```

Sobre la rama, la prueba falla (`Expected: 1, Received: 2`). Con el parche, pasa.

**Prevención**

Toda operación que mueve dinero o premios lleva una clave de negocio y una restricción de
unicidad en el servidor. La revisión de diseño pregunta: "¿qué pasa si esto llega dos veces?".

**Corrección de la versión vieja**

La versión vieja del incidente tenía dos ventas del mismo número. La causa era la misma:
la regla "un número se vende una vez" vivía en el store del navegador, no en el servidor.

<summary>✅ <b>Solución de referencia</b> — ábrela después de escribir la tuya</summary>

**Causa raíz**

`src/features/grants/grantSlice.js`, caso `sendGrant.rejected`: el reducer escribe
`failed` directamente, sin pasar por la función de transiciones. Un rechazo tardío (la
respuesta de un intento anterior que falló después de que el envío ya se había confirmado)
llega con `meta.arg` del envío y pisa `sent`. La UI muestra "Falló" con un error viejo.

El estado no tiene por qué ser incorrecto en el servidor: el servidor sí guardó el premio.
El defecto está en el cliente, que dejó que una acción fuera de orden cambiara el estado.

**Parche mínimo**

```javascript
.addCase(sendGrant.rejected, (state, action) => {
  transicion(state, action.meta.arg, "failed"); // solo desde sending: la tabla de transiciones decide
});
```

Con la transición validada, `failed` solo se alcanza desde `sending`. Un `rejected` que llega
después de `sent` se ignora.

**La refactorización correcta**

Toda escritura de estado de un envío pasa por la función de transiciones, sin excepciones.
Un reducer que escribe `status` directamente es un defecto de revisión. La prueba fija la
regla: una acción fuera de orden no cambia un estado terminal.

**Prueba de regresión**

```javascript
// src/__incidentes__/inc12.test.js — el envío llega a sent, después llega un rechazo tardío
store.dispatch({ type: sendGrant.rejected.type, payload: "tardío", meta: { arg: 401 } });
expect(store.getState().grants.byId[401].status).toBe("sent");
```

Sobre la rama, la prueba falla (`Expected: "sent", Received: "failed"`). Con la transición
validada, pasa.

**Prevención**

Las transiciones permitidas están escritas en una sola tabla. Una regla de revisión: si un
reducer toca `status`, la tabla está en el mismo archivo y la prueba de transiciones cubre
la acción.

**Si tu causa fue distinta a esta**

En la versión vieja del incidente había dos causas: una acción huérfana y una confirmación
pisada por un rollback. Aquí la acción huérfana es el rechazo tardío. Si encontraste un
segundo camino que pisa `sent`, es otra causa, y tiene su propio test.
